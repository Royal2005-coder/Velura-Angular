# v0.4 — the hook must not lie by omission

Status: **shipped 2026-09-04.** Both phases.

## Problem

The pre-edit hook de-duplicates per `(session, file)`: a file's decision
report fires on the first edit and is silent for the rest of the session.
That fixed a measured 5× repetition (2,063 bytes × 5 identical injections on
one file). It also introduced a lie by omission: **"silent" now means either
"nothing recorded" or "recorded, but you already saw it" — and the second
case stays silent even when what the agent saw is no longer true.**

Two ways it goes stale, in order of how often they will actually happen:

### 1. The agent lost the context it was shown

Long sessions compact. The report injected on edit #1 is summarised or
dropped; the marker file is not. From then on the agent edits a
`reversible: never` file with no context and the hook says nothing, because
from its point of view the job is done. Same shape on `--resume`: the marker
directory outlives the conversation that earned it.

This is the common case. Every session that runs long enough to compact
hits it, on every file it has already touched.

### 2. The record changed underneath the agent

Between edit #1 and edit #7, something real can land on the same file:

- a `Supersedes:` commit is merged and `ctx reindex` runs — the decision the
  agent is working against is now retired
- CI appends a `status: fail` run or an `open` incident
- the file is deleted (`removed:` appears)
- another commit adds a new stated decision to the same lines

Rarer, but these are exactly the events the tool exists to surface, and the
current hook cannot surface any of them a second time.

### What is *not* a problem

Re-showing after **unrelated** commits elsewhere in the repo. The report for
a file depends only on the commits that own its lines and the notes on those
commits. A commit to a different file does not change it. Any design that
keys on repository `HEAD` would re-fire on every commit anywhere and is
rejected up front.

## Design

Two mechanisms, one per vector. They are independent and each is worth
shipping alone.

### A. Invalidate on compaction and resume

Two more hook events, both trivial:

```json
"PostCompact":  [{ "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/ctx-forget.sh" }] }],
"SessionStart": [{ "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/ctx-forget.sh" }] }]
```

`ctx-forget.sh` reads `session_id` from stdin and removes
`$TMPDIR/ctx-hook-seen/<session_id>/`. The next edit to each file re-fires its
full report — which is correct, because the agent genuinely does not have it
any more. Cost after a compaction: one report per file the agent goes on to
touch, typically 2–5 files, ~2–10 KB total. That is the right cost; it was the
cost the agent had already paid once for the same knowledge.

Nothing in `ctx` itself changes. This is hook config plus a five-line script.

### B. Re-surface what changed, and only what changed

Replace the boolean marker with the **last-shown report JSON**, stored at
`$TMPDIR/ctx-hook-seen/<session>/<pathhash>.json`. On every edit after the
first:

```
current  = ctx for <path> -format json          # already computed for the `worth` check
delta    = ctx for <path> -since <baseline.json> # NEW: renders only what changed
if delta is non-empty: inject delta; save current as the new baseline
else: silent
```

`-since` is a small addition to the Go side, where the renderer already
lives. It loads the baseline `model.Report`, compares by SHA per section,
and emits a YAML fragment of additions only:

```yaml
since your last edit to platform/storage/minio-iscsi/pod-recovery.md:
superseded:
  - sha: 479ead91a3c0 -> by 9508a4b48107
    reason: V1 assumed the iSCSI transport was alive; this recurrence had a dead zombie session
open_incidents:
  - ec86c1e2e91a: Trino Iceberg reads failed with ICEBERG_INVALID_METADATA ...
```

What counts as a change, by section:

| section | fires on | rationale |
|---|---|---|
| `removed` | appears | the file was deleted mid-session; the agent is about to resurrect it |
| `superseded` | new SHA | the decision it was told about is now retired — the most important delta there is |
| `open_incidents` | new SHA | someone got hurt since it last looked |
| `orphaned` | new SHA | a constraint lost its code without review |
| `active` | new **stated** SHA | a new decision landed on these lines |
| `runs` | a new `fail` | a pass is noise; a fail is a warning |

Everything else — a `pass` run, a re-ordering, the agent's own unstated
commit becoming an owner — is silent. A whole report re-dump never happens
after the first edit.

The agent's own commits deserve a note. When the agent commits with a
`Decision:` trailer mid-session, its own commit becomes a new stated `active`
entry and the delta fires once with the decision the agent itself just
wrote. That is one small fragment per commit, bounded and harmless; trying
to detect "this is your own commit" from a shell hook is more machinery than
the noise costs.

## Phasing ⚑

- **Phase 1 — hook only. SHIPPED.** Mechanism A in full, plus the cheap version
  of B: store the current report JSON and re-fire the **full** report when its
  content hash differs from the baseline. Zero Go changes. Closes both
  vectors; the only cost over the final design is that a mid-session change
  re-dumps ~2 KB instead of a ~200-byte delta, once per change.
- **Phase 2 — `-since` in Go. SHIPPED.** Delta rendering, tests, and the hook switched
  to it. This is the token polish, not the correctness fix; it can wait for
  the field data the measurement gate is still waiting for.

Recommendation: ship Phase 1 now. It is small, it is entirely reversible, and
it turns "silent" back into a statement that means exactly one thing: nothing
you don't already have.

## Resolved — the subagent question, answered empirically

**Subagents share the parent's `session_id`.** Measured, not assumed: an
`Edit` from the parent and an `Edit` from a spawned subagent both arrived
carrying `session_id 9fb18989-…`. So the bug was real — the parent's marker
silenced a report the subagent had never seen.

**The mitigation this document originally proposed does not work.**
`transcript_path` is shared too — byte-identical across both invocations —
so keying on it would have changed nothing. That was a guess, and it was wrong.

The payloads differ in exactly one useful way: a subagent's carries
`agent_id` and `agent_type`; the parent's carries neither. The key is
therefore `session_id` + `agent_id`, with the parent bucketed under
`parent`. Each subagent gets its own bucket, and a compaction clears the
whole session subtree.

Full hook payload, for anyone building on this:
`cwd, effort, hook_event_name, permission_mode, prompt_id, scratchpad_dir,
session_id, tool_input, tool_name, tool_use_id, transcript_path`, plus
`agent_id` and `agent_type` when a subagent is the caller.

## What shipped in Phase 1

- **Mechanism A** — `ctx-forget.sh` on `PostCompact` and `SessionStart`,
  clearing `$TMPDIR/ctx-hook-seen/<session>/`.
- **Mechanism B (hash form)** — the marker stores an md5 of the report JSON
  rather than a boolean. Unchanged report → silent; changed → the full report
  fires again. One `ctx` call serves both the worth check and the change
  check, so a deduped repeat costs one ~50ms invocation and no tokens.

Verified matrix: parent fires then dedups; subagent A fires (own bucket) then
dedups; subagent B fires; opening an incident mid-session re-fires; a second
edit after that is silent at the new state; `PostCompact` re-fires. Regression
held: unadopted repos 0 bytes, resurrection still fires, no `session_id`
still fails open.

## Tests

- `ctx-forget.sh`: removes exactly its own session's directory, leaves other
  sessions' markers alone, exits 0 when the directory does not exist.
- Hook, Phase 1: same file twice → second is silent; append an incident note
  between the two → second fires; run `ctx-forget.sh` between the two →
  second fires the full report; different session → fires.
- `-since`, Phase 2 (Go, `render` + `ctxcmd`): empty delta → empty output and
  exit 0; each row of the table above fires exactly its own section; a `pass`
  run does not fire; a baseline file that is missing or unparseable falls back
  to the full report rather than to silence.

## Limits that remain

- **A change that lands during the same tool call** is not seen until the
  next edit. Nothing sits between "hook ran" and "edit applied".
- **Silence is still ambiguous to a human reading the transcript** — it
  cannot tell "nothing recorded" from "already shown, unchanged". The agent
  does not have this problem: it has the earlier injection or it has been
  compacted, and Mechanism A covers the second case.

## Phase 2, as shipped

`ctx for <path> -since <baseline.json>` diffs the current report against a
saved one and prints only what appeared, or nothing. The hook stores the
report JSON as the baseline and passes it on every later edit, so the first
sighting is a full report and everything after it is a diff.

Measured on one file: **897 bytes for the first fire, 269 for a delta
announcing one new incident** — and 0 while nothing changes. The delta also
drops the vocabulary preamble, which the agent only needs once, and says
"CHANGED while you were working in it" instead.

Two things the build corrected in this document's plan:

1. **A failed `-since` falls back to the full report, never to silence.** The
   first cut exited quietly when the flag errored, and a stale installed
   binary that predated the flag turned every delta into nothing at all —
   caught only because a test that should have fired didn't. A hook updated
   ahead of its binary must get louder, not quieter.
2. **`failed_runs` is its own section.** A failing run belongs to a commit
   already listed elsewhere in the report, so folding it into `active` or
   `superseded` would have re-sent an entry the reader already had.
